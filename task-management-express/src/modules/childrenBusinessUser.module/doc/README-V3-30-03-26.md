## 🎯 Overview

**Purpose**: Enables business users (parents/teachers) to manage child accounts and family team members. Handles parent-child relationships, permissions, and task assignment capabilities.

**Business Value**: Allows parents/teachers to create and manage multiple child accounts under one subscription, assign tasks, and monitor progress. Essential for family task management and parental control features.

**Users**: 
- **Business Users** (Parents/Teachers) - Create and manage child accounts
- **Child Users** - Managed accounts with task permissions
- **Secondary Users** - Trusted children with task creation privileges

## ✨ Key Features

- ✅ **Create Child Accounts** - Business users can add children to their family
- ✅ **Invitation Flow** - Optional flow where children set their own passwords (for teens 13+)
- ✅ **Profile Management** - Update child information (name, email, support mode, etc.)
- ✅ **Remove/Reactivate** - Soft delete and restore child accounts
- ✅ **Secondary User System** - Designate one child as "Task Manager" with special privileges
- ✅ **Team Members Dashboard** - View all children with task progress statistics
- ✅ **Family Members List** - Children can see their siblings
- ✅ **Permission Management** - Control which children can create tasks
- ✅ **Email Credentials** - Automatic email sending on account creation
- ✅ **Redis Caching** - Optimized queries for team members list and statistics

## 🏗️ Architecture Design

### Design Principles

1. **Parent-Child Relationship**: Direct relationship via `ChildrenBusinessUser` model (not through groups)
2. **Soft Delete**: Accounts are never hard deleted, only marked as `removed`
3. **Cache-First**: All read operations check Redis cache before database
4. **Async Email**: Email sending never blocks account creation
5. **Dual Flow Support**: Both parent-creates-password and child-sets-password flows

### Tech Stack
- **Database**: MongoDB (Mongoose)
- **Cache**: Redis (cache-aside pattern)
- **Email**: Nodemailer (SendGrid/AWS SES)
- **Validation**: Zod
- **Auth**: JWT (from auth module)

## 🔒 Security Notes

> **⚠️ Compliance & Security Considerations**

### COPPA Compliance (Children Under 13)
- ✅ **Parental Consent Required**: Only business users (parents/teachers) can create child accounts
- ✅ **Data Minimization**: Only collect necessary information (name, email, profile data)
- ✅ **Parental Control**: Parents can remove/reactivate child accounts at any time
- ✅ **No Third-Party Sharing**: Child data not shared with external services (except email provider)

### Data Protection
- ✅ **Password Hashing**: bcrypt with 12 rounds (industry standard)
- ✅ **Soft Delete**: Child accounts preserved (not permanently deleted)
- ✅ **Audit Trail**: `addedBy`, `addedAt`, `note` fields track account changes
- ✅ **Email Verification**: Children must verify email or use invitation flow

### Access Control
- ✅ **Role-Based Access**: Only business users can manage children
- ✅ **Relationship Validation**: Can only manage your own children
- ✅ **Rate Limiting**: Strict limits prevent abuse (3/hour for create)
- ✅ **JWT Authentication**: All endpoints require valid tokens

### Invitation Flow Security
- ✅ **Token Expiration**: 24-hour TTL prevents stale invitations
- ✅ **One-Time Use**: Tokens invalidated after activation
- ✅ **Crypto-Secure**: 64-character random tokens
- ✅ **Email Uniqueness**: Prevents duplicate accounts

### Service: Create Child Account

**Figma-Flow-Screenshot-File Name**: `figma-asset/teacher-parent-dashboard/team-members/create-child-flow.png`

**Endpoint**: `POST /children-business-users/children`  
**Role**: Business User (Parent/Teacher)  
**Auth**: Required  
**Rate Limit**: 3 requests/hour (strict)  
**Middleware**: `auth(TRole.business)`, `rateLimiter('strict')`, `validateRequest(createChildValidationSchema)`

<details>
<summary>🔄 <b>Click to view Flow Diagram</b></summary>

```
Parent (Business User)
    ↓
POST /children-business-users/children
    ↓
Controller: createChild()
    ↓
Service: createChildAccount()
    ├─→ Verify business user exists
    ├─→ Check email uniqueness
    ├─→ Hash password (bcrypt 12 rounds)
    ├─→ Create UserProfile (supportMode, location, dob, gender)
    ├─→ Create User account (role: child)
    ├─→ Create relationship record
    ├─→ Send credentials email (async)
    ├─→ Invalidate Redis cache
    └─→ Return { childUser, relationship }
    ↓
Response: 201 Created
```

</details>

- `children:business:{userId}:count` (TTL: 10 min) → Invalidate in `createChildAccount()` after relationship creation

## 🗄️ Redis Caching

| Key Pattern | TTL | Use Case | Where to Invalidate |
|-------------|-----|----------|---------------------|
| `children:business:{userId}:children` | 10 min | Cache children list | `createChildAccount()`, `updateChildProfile()`, `removeChildFromFamily()`, `reactivateChild()`, `setSecondaryUser()` |
| `children:business:{userId}:count` | 10 min | Cache children count | `createChildAccount()`, `updateChildProfile()`, `removeChildFromFamily()`, `reactivateChild()` |
| `children:team-list:{userId}:page-{page}-limit-{limit}` | 3 min | Cache team members list with pagination | `updateChildProfile()`, `setSecondaryUser()` |
| `children:team-statistics:{userId}` | 5 min | Cache team statistics | `getTeamMembersStatistics()` (cache after build) |
| `activation:token:{token}` | 24 hours | Store invitation tokens | `activateAccount()` (delete after activation) |

### Cache Strategy

**Pattern**: Cache-aside (lazy loading)

**On Read**:
1. Check Redis cache
2. If hit → return cached data
3. If miss → read from database
4. Cache result
5. Return data

**On Write**:
1. Perform database operation
2. Invalidate related cache keys
3. Return response

## 🐛 Troubleshooting

### Issue: Email not sent after account creation

**Symptom**: Account created but child doesn't receive credentials email

**Solution**: Check SMTP configuration in `.env` and error logs

```bash
# Check SMTP configuration
cat .env | grep SMTP

# Check error logs
tail -f logs/error.log | grep "email"
```

---

### Issue: Redis cache not invalidated

**Symptom**: Updated child data not reflected in list views

**Solution**: Check Redis connection and manually clear cache

```bash
# Check Redis connection
redis-cli ping  # Should return: PONG

# Check cache keys
redis-cli
KEYS children:*

# Manually clear cache
redis-cli
FLUSHDB
```

---

### Issue: Token already used or expired

**Symptom**: Child can't activate account, gets "Invalid or expired token"

**Solution**: Check token in Redis

```bash
# Check token in Redis
redis-cli
GET activation:token:abc123xyz

# Check token expiration
TTL activation:token:abc123xyz
```
