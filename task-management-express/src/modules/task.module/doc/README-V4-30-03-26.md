## 🎯 Overview

**Purpose**: Core task management module enabling creation, assignment, and tracking of personal and collaborative tasks with subtask progress tracking.

**Business Value**: Allows parents/teachers to assign tasks to children, track individual progress on collaborative tasks, and monitor overall task completion. Essential for family task management and accountability.

**Users**:
- **Business Users** (Parents/Teachers) - Create tasks, assign to children, monitor progress
- **Child Users** - View assigned tasks, update progress, complete subtasks
- **Secondary Users** - Trusted children with task creation privileges

## ✨ Key Features

- ✅ **Task Creation** - Create personal, single-assignment, or collaborative tasks
- ✅ **Task Assignment** - Assign tasks to individual children or multiple children
- ✅ **Subtask Management** - Break tasks into subtasks with individual progress tracking
- ✅ **Progress Tracking** - Track individual child progress on collaborative tasks
- ✅ **Task Statistics** - Get task counts by status (pending, in-progress, completed)
- ✅ **Daily Task Limits** - Enforce maximum tasks per day (prevents overload)
- ✅ **Task Filtering** - Filter by status, type, priority, date range
- ✅ **Dashboard Integration** - Optimized views for parent and child dashboards
- ✅ **Redis Caching** - Cached task lists and statistics for performance
- ✅ **Real-time Updates** - Socket events for task assignments and completions

## 🏗️ Architecture Design

### Design Principles

1. **Task Type Flexibility**: Support personal, single-assignment, and collaborative tasks
2. **Subtask Separation**: Subtasks stored in separate collection for scalability
3. **Individual Progress Tracking**: Each child's progress tracked separately for collaborative tasks
4. **Cache-First**: All read operations check Redis cache before database
5. **Permission-Based Access**: Secondary User system for task creation by children

### Tech Stack
- **Database**: MongoDB (Mongoose)
- **Cache**: Redis (cache-aside pattern)
- **Validation**: Zod
- **Auth**: JWT (from auth module)
- **Real-time**: Socket.io (for task updates)

## 🔒 Security Notes

> **⚠️ Compliance & Security Considerations**

### Data Protection
- ✅ **Soft Delete**: Tasks are never hard deleted, only marked as `isDeleted`
- ✅ **Access Control**: Users can only access tasks they created, own, or are assigned to
- ✅ **Audit Trail**: `createdById`, `startTime`, `completedTime` track task lifecycle

### Access Control
- ✅ **Role-Based Access**: Business users always allowed; Child users need Secondary User permission
- ✅ **Task Ownership Validation**: Middleware verifies user relationship to task
- ✅ **Rate Limiting**: Strict limits prevent abuse (20/hour for create, 100/min for read)
- ✅ **JWT Authentication**: All endpoints require valid tokens

### Task Creation Security
- ✅ **Daily Task Limits**: Maximum tasks per day enforced (prevents spam/overload)
- ✅ **Secondary User Check**: Only trusted children can create tasks
- ✅ **Task Type Validation**: Ensure consistency between task type and assignment

### Service: Create Task

**Figma-Flow-Screenshot-File Name**: `figma-asset/teacher-parent-dashboard/task-monitoring/create-task-flow/create-task.png`

**Endpoint**: `POST /tasks`  
**Role**: Business User (Parent/Teacher) or Secondary User (Child)  
**Auth**: Required  
**Rate Limit**: 20 requests/hour  
**Middleware**: `auth(TRole.commonUser)`, `createTaskLimiter`, `checkSecondaryUserPermission`, `validateRequest(createTaskValidationSchema)`, `validateTaskTypeConsistency`, `checkDailyTaskLimit`

<details>
<summary>🔄 <b>Click to view Flow Diagram</b></summary>

```
User (Business or Secondary Child)
    ↓
POST /tasks
    ↓
Controller: create()
    ↓
Service: createTask()
    ├─→ Validate daily task limit (for personal tasks)
    ├─→ Auto-set ownerUserId for personal tasks
    ├─→ Auto-calculate subtask counts
    ├─→ Create task in database
    ├─→ Bulk create subtasks (if provided)
    ├─→ Auto-create TaskProgress records for assigned children
    ├─→ Invalidate Redis cache
    ├─→ Emit socket event (task.created)
    └─→ Return { task }
    ↓
Response: 201 Created
```

</details>

**Redis Cache Keys Invalidated**:
- `task:user:{userId}:list` (TTL: 5 min) → Invalidate in `createTask()` after task creation
- `task:user:{userId}:statistics` (TTL: 5 min) → Invalidate in `createTask()` after task creation

**Socket Events**:
- emits: `task.created` (to assigned users)

## 🗄️ Redis Caching

<details>
<summary>📦 <b>Click to view Redis Caching Details</b></summary>

| Key Pattern | TTL | Use Case | Where to Invalidate |
|-------------|-----|----------|---------------------|
| `task:detail:{taskId}` | 5 min | Cache task details | `updateTask()`, `deleteTask()` |
| `task:user:{userId}:list` | 5 min | Cache user's task list | `createTask()`, `updateTask()`, `deleteTask()` |
| `task:user:{userId}:statistics` | 5 min | Cache task statistics | `createTask()`, `updateTask()`, `deleteTask()`, `getStatistics()` (cache after build) |
| `task:dashboard:children:v4:{userId}:{page}:{limit}` | 5 min | Cache dashboard tasks | N/A (read-only cache) |
| `task:detail:{taskId}:parent` | 5 min | Cache parent task details | N/A (read-only cache) |

### Cache Strategy

**Pattern**: Cache-aside (lazy loading)

**On Read**:
1. Check Redis cache
2. If hit → return cached data
3. If miss → read from database
4. Cache result
5. Return data

**On Write**:
1. Perform database operation
2. Invalidate related cache keys
3. Return response

## 🐛 Troubleshooting

<details>
<summary>🐛 <b>Click to view Troubleshooting Details</b></summary>

### Issue: Can't create task - daily limit exceeded

**Symptom**: Error message "You can only create X tasks per day"

**Solution**: This is expected behavior - daily task limit prevents overload

```bash
# Check how many tasks exist for today
db.tasks.countDocuments({
  ownerUserId: ObjectId("YOUR_USER_ID"),
  startTime: {
    $gte: new Date("2026-03-30T00:00:00.000Z"),
    $lt: new Date("2026-03-30T23:59:59.999Z")
  }
})
```

---

### Issue: Task not found or access denied

**Symptom**: 404 Not Found or 403 Forbidden when accessing task

**Solution**: Verify user has access to task (creator, owner, or assigned)

```bash
# Check task details
db.tasks.findOne({ _id: ObjectId("task123") })

# Verify user relationship
db.tasks.findOne({
  _id: ObjectId("task123"),
  $or: [
    { createdById: ObjectId("YOUR_USER_ID") },
    { ownerUserId: ObjectId("YOUR_USER_ID") },
    { assignedUserIds: ObjectId("YOUR_USER_ID") }
  ]
})
```

---

### Issue: Redis cache not invalidated

**Symptom**: Updated task data not reflected immediately

**Solution**: Check Redis connection and manually clear cache

```bash
# Check Redis connection
redis-cli ping  # Should return: PONG

# Check cache keys
redis-cli
KEYS task:*

# Manually clear cache
redis-cli
FLUSHDB
```

---

### Issue: Subtasks not showing in task details

**Symptom**: Task returned without subtasks array

**Solution**: Verify virtual populate is configured correctly

```bash
# Check if subtasks exist in SubTask collection
db.subtasks.find({ taskId: ObjectId("task123") })

# Verify virtual populate in query
# Should include: { path: 'subtasks', select: '-__v -isDeleted' }
```
